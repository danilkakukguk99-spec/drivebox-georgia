# DRIVEBOX: запуск обработки заказов

Сайт теперь требует Python-сервер и постоянный диск для SQLite. Обычная статическая публикация через Netlify/GitHub Pages не обслуживает API заказов. Хостинг ещё не выбран пользователем. Ничего не опубликовано.

## Локальный запуск

`python3 server/store.py` — сайт и API на http://localhost:8000. Локальный `.env` содержит случайный пароль менеджера; файл исключён из Git и Docker. Страница менеджера: `/admin.html`. Изменить пароль можно в `.env`, затем перезапустить сервер. Не отправляйте секреты в переписку.

По умолчанию разрешён только явно помеченный тестовый заказ. База: `data/orders.sqlite3`. Тесты используют отдельную временную базу, не рабочие заказы.

## Настройка перед реальными продажами

Скопировать переменные из `.env.example` в секреты хостинга:

- APP_ENV=production, PUBLIC_URL=https://ваш-домен (без завершающего слеша).
- DATA_DIR — постоянный закрытый диск, не каталог статической публикации. Для production используйте новую базу без демонстрационных заказов.
- ADMIN_PASSWORD — уникальный пароль минимум 16 символов.
- SELLER_NAME, SELLER_ID, SELLER_ADDRESS, SELLER_PHONE, SELLER_EMAIL, SELLER_WHATSAPP — реальные данные продавца. SELLER_EMAIL также получает уведомления.
- ALLOW_COD=true — только если магазин действительно принимает оплату при получении.
- SMTP_HOST, SMTP_PORT=587, SMTP_USER, SMTP_PASSWORD, SMTP_FROM — подтверждённый почтовый отправитель с STARTTLS. Проверить доставку покупателю и менеджеру, SPF/DKIM в почтовом сервисе.
- FULFILLMENT_CONFIRMED=true — после подтверждения наличия, закупки, гарантии и реальных сроков доставки.
- LEGAL_CONFIRMED=true — после заполнения политики хранения данных и окончательных условий продавца. Текущие юридические страницы остаются проектом, их нельзя выдавать за согласованные документы.
- DISCOUNT_PERCENT и FREE_SHIPPING — утверждённая акция. Значения по умолчанию сохраняют текущие 15% и бесплатную доставку.

При неполных production-настройках сервер блокирует создание заказов. Панель менеджера показывает недостающие настройки. Это проверка заполненности, а не подтверждение доступности внешних сервисов.

## PayPal

Обновлённая интеграция SDK v6, карта/PayPal/COD, актуальные статусы, Sandbox-сценарии и Live-переход подробно описаны в PAYPAL_SETUP.md. Для платежей используйте эту новую инструкцию.

Текущая интеграция подготовлена для PayPal; подключение другого банка требует его учётных данных и адаптера API.

1. Для испытаний задать PAYPAL_ENV=sandbox и sandbox CLIENT_ID/CLIENT_SECRET/WEBHOOK_ID. Для реальной работы — PAYPAL_ENV=live и соответствующие реальные данные.
2. Зарегистрировать HTTPS endpoint `/api/paypal/webhook`. События: CHECKOUT.ORDER.APPROVED, PAYMENT.CAPTURE.COMPLETED, PAYMENT.CAPTURE.PENDING, PAYMENT.CAPTURE.DENIED, PAYMENT.CAPTURE.REFUNDED, PAYMENT.CAPTURE.REVERSED.
3. Клиентский секрет хранится только на сервере. Заказ PayPal и capture выполняет сервер. Подпись webhook проверяется через PayPal. Повторные create/capture используют постоянные PayPal-Request-Id.
4. Цены в GEL; PayPal получает USD. GEL_PER_USD задаёт утверждённый продавцом курс, сумма USD фиксируется для каждого заказа и показывается покупателю до перехода в PayPal. Это управляемый фиксированный курс, не автоматический рыночный курс.
5. Проверить sandbox оплату, отмену, отказ, повторный webhook и восстановление после закрытия вкладки. Без учётных данных реальный сетевой цикл PayPal не проверен.
6. Возвраты выполняются в кабинете PayPal. Возврат ставит статус refunded/partially_refunded, реверс — review_required; автоматического возврата и отмены PayPal-заказа через админку пока нет.

Документация: https://developer.paypal.com/api/rest/webhooks/ и https://developer.paypal.com/reference/guidelines/idempotency/

## Запуск на сервере

`pip install -r requirements.txt`

Веб-процесс: `gunicorn -c gunicorn.conf.py server.store:application`

Отдельный единственный worker: `python3 -m server.worker`

Либо собрать Dockerfile и запустить web и worker с одним постоянным томом `/data` и одинаковыми секретами. HTTPS и перезапуск процессов обеспечивает хостинг/reverse proxy. Используется один web worker с потоками: in-memory ограничения частоты рассчитаны на один процесс. При масштабировании нужен общий rate-limit и PostgreSQL. Настроить ограничения частоты на reverse proxy; не доверять произвольному X-Forwarded-For.

Worker отправляет почту с повторными попытками и сверяет неоплаченные PayPal-заказы последних 3 дней. Webhook остаётся основным каналом оплаты. Неполученные письма видны счётчиком в админке. Не запускайте несколько mail-worker одновременно.

## Работа менеджера

- `/admin.html`: вход, последние 500 заказов, фильтр, CSV, статусы, доступные остатки.
- Новый → подтверждён → отправлен → доставлен. Неоплаченный PayPal нельзя отправить.
- Для оплаты при получении после доставки отдельно подтвердить получение денег.
- Отмена неплатёжного заказа возвращает резерв на склад. Неоплаченные PayPal-резервы проверяет менеджер; автоматического освобождения нет.
- Остаток null в исходном каталоге означает отсутствие количественного ограничения. Перед запуском задать реальные остатки через админку. Цены и названия для расчёта находятся в `server/catalog.json`; публичная витрина получает их через API.
- CSV содержит персональные данные: хранить в закрытом месте.

## Резервное копирование

`python3 -m server.backup /закрытый/путь/orders-YYYY-MM-DD.sqlite3`

Настроить ежедневный запуск средствами хостинга и копирование в отдельное приватное хранилище. Проверить восстановление на отдельной базе. Срок хранения и удаление персональных данных необходимо утвердить с продавцом; автоматическое удаление не включено.
